# Magic, from choosing a spell to its last consequence

Commit `78a9735` gave a cast an identifiable source. Commit `f092ad9` made target selection, spread and backfire ordinary steps within a deed spell's release. Keep both gains. The remaining question is which decisions belong to selection, release and impact. Those moments can disagree for good game reasons. Keeping every intermediate figure in sync obscures that distinction.

## What exists between those moments?

| Primitive | What gives it a lifetime | Who owns it |
| --- | --- | --- |
| Knowledge of a spell | The actor can select it on future turns. Learning and losing it change the repertoire. | The learned spell and its relationship to the caster. Its definition supplies realm, price and targeting rules. |
| A casting source | Two identical wands can have different bearers and charges. A learned spell spends from a realm. A monster slot has its own casting rules. | Refer to the actual learned spell, item or slot. Read bearer, charges, realm points and slot rules where each lives. |
| An order to cast | The player or AI can choose now and act later. The chosen target may leave or the source may become unavailable. | The pending action owns the source, intended aim and requested power. Preserve the distinction between an explicit power and an automatic choice. |
| A released effect | The source can be consumed or the caster can change before the last hit. | Where delivery spans time, the deed or projectile owns resolved strength, attribution and the targets or geometry fixed at release, as required by that working. |
| An enchantment | It can expire or be dispelled independently of the original action. | The active effect owns its subject, magnitude and duration. Removal ends its contribution. |
| A saved portal | A later cast can return to a previously recorded place. | Store the destination on its owner. Marking the place is the entire immediate effect. |

A source reference answers *which one?* It grants no authority to use it. Resolve ownership when executing the order. This is the same inventory relationship a transfer changes. Finishing a released effect must still work after the last charge consumes the item.

## Follow one learned spell

1. Opening the book enumerates learned spells. Ask which powers the caster can afford from this realm now. For the selected row or power picker, compute failure at the powers it displays. The calculation takes the spell and borrows the caster's actual skills and levels. It returns a value and consumes no randomness.
2. Choosing a spell records the order. Opening a second view, changing the highlighted target, or closing the book has no gameplay consequence.
3. At execution resolve the source again, check eligibility in the current activity, and resolve the intended target. Price the requested power under the applicable rule. An automatic repeat has to qualify again after paying for its previous cast. Keep refusal, a failed casting roll and a successful release distinct because their costs and consequences can differ. Preserve each source's payment and practice rules.
4. Roll once the inputs for that decision are known. An immediate working can use local values through completion. For delayed delivery, retain the decisions already made. Read an impact-time defence at impact when the rule calls for it. Reporting, reflection, practice and a repeat can consume the outcome of the completed deed. A future cast gets its own decision.

The retail check for a recorded order checks learned status, context and cost, and outside combat checks whether the target is still valid. It prices the affordable-power request at one for this admission check. Distinguish this check from selecting the actual affordable power. The casting skill calculation also prices failure for a particular spell and power. These are evidence for when to ask each question. ## What the rewrite can delete

- **Per-spell copies of the caster.** Spending from one realm changes one pool. Today it can also change many learned entities' `MostPower`. The executor already reads the pool directly, while taking `FailsAt`, `StrengthFigure` and `Boost` from the spell. One release thus uses figures with two different freshness guarantees. Remove these projections together with `SeesBlind` and `Barred`. Share eligibility and power functions between the book and execution. Explicit power needs one failure calculation. Automatic power can evaluate the alternatives locally. The UI can retain display rows while open. No gameplay reader should consume them. [Castables](../../src/game/magic/castable.rs) · [Casting rules](../../src/game/magic/casting/means.rs)
- **The party's copy of the circumstances.** A conversation already knows whether it awaits a reply. Device interaction already distinguishes picking from disarming. Movement owns ground contact. Let the casting eligibility query borrow these owners through their existing domain accessors. Compute the relevant context once for a book read or cast, including precedence when activities coexist. Introduce a shared party activity only for mutually exclusive activities that really acquire and release control of the party. Footing remains an independent question. The eligibility query must preserve the unresolved looting case as an explicit port uncertainty. [Occasion](../../src/game/magic/occasion.rs)
- **The utility cast as a sequence of markers.** Setting a portal currently marks an empty target, then a later handler performs the work. Returning checks for a destination. Identifying an item needs an actual item target. Give each working a typed operation taking what it uses. Validate its target before spending or rolling where required, then pass the validated value directly to its effect. Keep the source-specific casting rules shared. The portal operation writes a destination and Identify changes the selected item's knowledge. Neither needs an entity solely to carry an argument between observers. A cross-level return can hand its destination to the existing travel operation, whose completion really does take time. [Portal handlers](../../src/game/magic/portals.rs) · [Item workings](../../src/game/magic/utilities.rs)

## The same mistake outside magic

**Armour is the clearest second rewrite.** Several systems write individual cells of `ArmourParts`, even for a change as small as crossing a Speed threshold. Defending adds and removes a contribution through observers. Another system reduces the cells into total, penetration and a hit-location-weighted average. This makes a strike after an equipment swap depend on a sequence of writes across inventory, actor figures and armour. Retail's `CalcArmorClasses` explicitly clears and rebuilds its component array. Preserve its slot rules, conditional contributions, thresholds and rounding. Its scratch array need not become a permanent Bevy component. [Armour](../../src/game/actors/armour.rs) · [Retail GameplayCode.cpp](../../../wizardry-8-decomp/src/wiz8/local_code/GameplayCode.cpp)

Keep equipment relationships, item protection, stance and conditions as independently writable inputs. Give armour one calculation that can publish the bearer's protection by hit location as a separate derived component. A blow reads the relevant location and applies strike-specific terms. The sheet can weight the locations using the body's hit distribution and ask the same rule for a breakdown when needed. Moving a shield to the inactive set changes the equipment relationship. The next blow must see that move even when both happen in one turn. [Source ownership and propagation](code-architecture.md#separate-the-inputs-to-a-rule-from-its-derived-components)

**Pressing is a smaller complete example.** Its system visits actors, reads Speed, aim bonus and fatigue, follows the first arm, reads its rating and whether it is modern, and writes one integer. During a blow these are a coherent query about its participants. Compute the score for the participants there, sharing the same rule wherever that score is needed. A weapon swap changes which arm the query sees. Introducing an additional kind of arm should require supplying its rating and fatigue rule at the arm, with no actor-wide refresh. [Actor figures](../../src/game/actors/figures.rs)

**Formation shows where to stop.** A dead member's former row cannot be reconstructed from the present seats. Keep it. Whether two members are screened by the centre can be answered from the seats when considering a blow. Formation already makes this distinction. For every proposed component, ask what a reader would lose if it vanished and the reader still had access to the owners. History, a pending choice, an independently expiring effect or a measured index with a clear invalidation owner can justify storage. A second way to obtain today's answer creates a scheduling obligation. [Formation](../../src/game/party/formation.rs)
